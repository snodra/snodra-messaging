# Sagas S1 (Kotlin) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Axon-style sagas, deadlines and the external-integration toolkit in the Kotlin library `kraken-messaging`, persisted in each service's MongoDB, fed by its Kafka consumer, with a test fixture and a sandbox example.

**Architecture:** A saga runtime inside the library: annotated saga classes are discovered at startup; events from `kraken.events` (and from the three inbound channels) reach a shared local dispatcher that runs the ordinary `@EventHandler`s in their transaction and then each saga type in its own transaction (state with optimistic version, association lookup, exactly-once marker). Commands and events a saga emits are recorded in `saga_dispatch` and sent after commit by an ordered relay; deadlines live in `deadlines` and fire from a leased poller. Adapters are ordinary command handlers made idempotent by `@IdempotentHandler` over `external_calls`.

**Tech Stack:** Kotlin 2.4, Spring Boot 4.1, Spring Data MongoDB (thread-bound transactions), Spring Kafka, Jackson (the library's `JsonCodec`), Micrometer (optional, `compileOnly`), JUnit 5 + Testcontainers (`kraken-messaging-test`'s `KrakenContainers`).

**Spec:** `kraken-messaging/docs/superpowers/specs/2026-10-31-sagas-design.md` (approved 2026-11-03). Roadmap row S1 in `kraken/docs/superpowers/specs/2026-10-31-hub-axon-parity-design.md`.

## Global Constraints

- Spring Boot 4.1, Kotlin 2.4. Saga, deadline and `@IdempotentHandler` handlers are **non-suspend** (thread-bound Mongo transactions); a suspend one is a startup error naming class and method.
- No new infrastructure: MongoDB and Kafka only. No new runtime dependency except what Spring Boot already manages; Micrometer stays `compileOnly` (bind meters only when a `MeterRegistry` bean exists, as `HubAuthMetrics` does).
- Configuration under `kraken.messaging.sagas.*`, `kraken.messaging.deadlines.*`, `kraken.messaging.external.*`. The saga runtime, dispatch relay and deadline scheduler start only when at least one `@Saga` class exists; `external_calls` indexes and the idempotency interceptor only with an `@IdempotentHandler`; external consumers only with a configured source.
- Sagas only speak kraken messages: no HTTP client, no foreign producer in the saga runtime.
- Collection names and field names exactly as the spec's Storage table (they are the Rust S2 contract); add only what this plan names (marked).
- Commit messages end with exactly `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`.
- Docker-backed test runs go through the workspace lock wrapper when another agent may run Testcontainers.

## Builder rulings (made while planning; each goes into ADR 0021 with its cost if wrong)

- **R1. One saga transaction per (event, saga type)**, marker `processed_events` id `saga:<sagaType>:<eventId>` (spec: one saga transaction per event, marker `saga:<eventId>`). Reason: a broken handler in one saga type must not hold back or roll back other saga types (anti-goal "a saga that silently stops"), and `saga_failures._id = <sagaType>:<eventId>` already parks per type. Cost: one transaction per interested saga type per event.
- **R2. Shared `LocalEventDispatcher`** extracted from `EventConsumer`: stage 1 the ordinary handlers in one transaction with marker `<eventId>` (unchanged behaviour), stage 2 the saga runtime (R1). Used by the Kafka consumer, external Kafka sources and the webhook ingress. A record with no ordinary handler but saga interest is no longer skipped.
- **R3. Order of stages:** ordinary handlers first, then sagas; both before the offset is acknowledged. A redelivered record finds stage 1's marker and goes straight to stage 2.
- **R4. Bounded saga retry inside stage 2** (default 5 attempts, backoff 200 ms ×2 up to 5 s) for version conflicts, start-key duplicates and handler exceptions; then park in `saga_failures` together with the marker, so stage 2 never throws to the consumer.
- **R5. `SendOptions.headers`** (new, default empty) carries extra request headers to the hub and to the local short-circuit's `MessageContext.headers`; the relay uses it for `idempotency-key` and `saga-id`. Reserved header names (`authorization`, trace headers) cannot be overridden.
- **R6. `SagaCommandFailed` is dispatched locally** through `LocalEventDispatcher` (dedupe key `failed:<dispatchId>`), never published to `kraken.events`.
- **R7. Deadline payload type** stored as the payload class's message type name if it has `@MessageType`, else its FQCN.
- **R8. Defaults:** relay poll 500 ms, saga lease 30 s; deadline poll 1 s, lease 30 s; `IN_PROGRESS` lease of `external_calls` 5 min; relay transient retry 10 attempts, backoff 1 s ×2 up to 5 min; `sagas` TTL of ended 30 days; `saga_dispatch` TTL of dispatched 7 days; deadlines TTL of fired/cancelled 7 days; `external_calls` TTL 30 days.
- **R9. ADR number 0021** (the spec's "0013" is taken by hub protocol versioning).
- **R10. Fake printer** is a Kotlin Spring Boot module `examples/fake-printer` (same toolchain as the examples; spec leaves the language open).

## Review Focus

1. An event that both matches a live instance and a `@StartSaga` handler (`forceNew = false`) is handled once, by the existing instance, never by a new one. → test in Task 5.
2. Two events for the same saga instance processed concurrently (two service instances, or the consumer plus the webhook ingress): one commits, the other conflicts, retries and applies on the new state; neither is lost or applied twice. → test in Task 5.
3. Crash between the saga commit and the relay's dispatch, and between dispatch and "mark dispatched": the command is (re)sent with the same `idempotency-key`, and an `@IdempotentHandler` adapter runs its body once. → tests in Tasks 6 and 9.
4. A saga that ends while deadlines are scheduled and dispatch entries are pending: deadlines are cancelled; already committed dispatch entries are still dispatched in order. → tests in Tasks 6 and 7.
5. One saga type's handler throws on every attempt while another saga type is interested in the same event: the second type handles it normally; the first parks in `saga_failures`; `SagaFailures.retry` later applies it exactly once. → tests in Tasks 5 and 8.
